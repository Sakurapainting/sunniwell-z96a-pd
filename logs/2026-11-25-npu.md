# Z96A RKNPU 实机验证 · 2026-11-25

## 原厂设备树与供电

从本机 eMMC 只读提取原厂 Android `boot`（`mmcblk0p8`）和 `dtbo`（`mmcblk0p6`）。镜像和提取件位于 `local/npu/`。`boot` 中 Rockchip `rk-kernel.dtb` 资源和 Android v2 DTB 段里的 DTB 字节一致，SHA-256 为 `f7645885ab0eb90ae1847b7e4f497bc04b2f17ef912dda10f0c751ad2584bf4f`。型号为 `Sunniwell RK3568 RH218 V01 Board`。成功叠加原厂 DTBO，叠加内容仅涉及 `/chosen` 的 Android 启动参数和 reboot-mode。

| 项目 | 同板原厂 DTB | BSP 试验配置 |
| --- | --- | --- |
| NPU 核心 | `npu@fde40000`，启用，共享 GIC SPI 151 | 启用，时钟、复位、中断索引相同 |
| IOMMU | `iommu@fde4b000`，启用，CRU 时钟 40/41，电源域 6 | 启用，规格相同 |
| NPU 时钟 | SCMI 2，CRU 35/40/41；核心初始 600 MHz | 相同 |
| NPU 复位与电源域 | CRU 43/44；`power-domain@6` | 相同 |
| `rknpu-supply` | RK809 `DCDC_REG4` / `vdd_npu`，DT 钳位 500–1350 mV，初始 900 mV | 接同一稳压器，试启后板端在 600 MHz 报 875 mV |
| 核心 OPP | 200/300/400 MHz 默认 850 mV；600 MHz 默认 875 mV；700/800/900 MHz 为更高 OPP，1 GHz 禁用 | 保留 BSP 的 600 MHz 上限，普通 600 MHz 项改用原厂默认 875 mV；实际板端可选频率 200/297/400/600 MHz |
| `bus-npu` | SCMI 2，`clkfreq` 方式，占用 DCDC_REG1 / `vdd_logic`，PVTM 参考 `vdd_cpu`；700/900/1000 MHz 表，默认 900/900/950 mV | 核对表值一致，保留独立总线调压节点禁用。RKNPU 驱动自身仍控制 SCMI 时钟，空闲曾读到 198 MHz |

原厂 U-Boot 也报告 `PMIC: RK8090` 及 `vdd_npu init 900000 uV`。以上电源结论来自同板原厂设备树、U-Boot 和 Linux 软件读数。

## 一次性启动和驱动绑定

2026-11-25，使用 U-Boot `sysboot mmc 0:a any 0x00c00000 /var/lib/linux-rockchip-z96a/bootcheck-6.1.172-7-npu/extlinux.conf`。试启目录使用正式 `-7` Image 和 initramfs 的硬链接，启动参数同正式 BSP 试启，仅加载独立的 NPU DTB。DTB SHA-256 为 `7f156790c2a88a8fa5ecfe7d00808c06e5c03648ea1af894a93beafb1024e41b`。逐文件校验 `/boot` 与原验收清单一致，extlinux 默认 `linux`。

运行 `6.1.172-7-z96a-bsp61`，boot ID 为 `d3977954-c12c-4b20-abb4-b691d7b3ff39`。RKNPU 驱动 `0.9.8`、`rk_iommu` 绑定成功，NPU 使用 IOMMU group 0，创建了 `/dev/rknpu`。探测期有两条诊断。内存资源重叠时驱动走 `devm_ioremap` 回退；原厂 DT 中 NPU 无 `interrupt-names`，当前 BSP 先按 `npu_irq` 查找，再按索引 0 成功注册共享 IRQ。`/proc/interrupts` 看到实际推理增加 `fde40000.npu` 所在 IRQ 的计数。

Rockchip 官方 Linux aarch64 `librknnrt.so` 取自 `airockchip/rknn-toolkit2` 的 `v2.3.2` tag，SHA-256 为 `d31fc19c85b85f6091b2bd0f6af9d962d5264a4e410bfb536402ec92bac738e8`。官方 MatMul demo 的 INT8 × INT8 → INT32 测试（4×64 乘 64×32，20 次）通过 CPU 结果比对。demo 对 RK3568 尝试设置核心掩码时打印错误，随后仍完成计算和比对。

## 图像模型输出和 DMA heap 对照

官方 RK3566/RK3568 MobileNet V1 和 ResNet18 均能完成运行。初测有间歇性错误，API 返回成功但分类与官方参考不一致。MobileNet 在 200、400、600 MHz 都见过异常，加日志或降频仍未消除。ResNet18 以 softmax 后的概率对照参考；错误时曾返回全相同的 logits。

测试进程可以用 `uncached-heap.so` 将官方 Runtime 对 `/dev/dma_heap/system` 的 `open()` 定向到 `/dev/dma_heap/system-uncached`。保持同一 Runtime、同一模型和内核，不修改系统设备、库或权限。第一组独立初始化各 12 次，默认 heap 下 MobileNet 通过 9/12、ResNet18 通过 12/12，uncached heap 下均通过 12/12。此对照用于定位缓存路径，输出偏差的根因仍待验证。

第二组交替初始化同时测试默认 heap 与 `system-uncached`，每个模型每种设置 32 次，四组均通过 32/32。这组对照未复现之前的间歇性偏差。进一步在每次确认平台设备 `runtime_status=suspended` 后启动 MobileNet，默认 heap 和 `system-uncached` 各通过 8/8。

| `system-uncached` 连续测试（实测 600 MHz） | 结果 | NPU 负载，均值 / 峰值 | 期间内核日志 |
| --- | --- | --- | --- |
| 官方 MobileNet V1，`dog_224x224.jpg` | 30.004 秒，4,555 次全部通过，首选类别 156（Shih-Tzu），概率 0.935059 | 72.2% / 76% | 无新增 |
| 官方 ResNet18，`space_shuttle_224.jpg` | 30.007 秒，2,653 次全部通过，首选类别 812（space shuttle），softmax 概率 0.999680 | 87.3% / 91% | 无新增 |
| RK3568 FP16 3×3 Conv，交替使用两组输入 | 30.002 秒，11,355 次，每次核对 14,400 个元素，最大绝对偏差 0 | 1.9% / 2% | 只记录 eDP 模式设置 |

相同的 FP16 Conv 在默认 heap 另跑 15.000 秒，24,309 次均与 CPU 结果逐元素完全一致。频率采样均为 600 MHz，NPU 负载均值 7.8%、峰值 9%，内核无新增日志。

卷积模型 ONNX 和 RKNN 文件在 `local/npu/conv/`，`make-model.py` 用官方 Toolkit2 2.3.2 转换，编译器逐算子记录把卷积安排到 NPU。`conv-check.c` 在 CPU 上独立计算两组参考值。`conv.rknn` 的 SHA-256 是 `782e083e826d9b92cdc3f0ba914ea1c86ea35f55c69e8709bcfc5caf09e83846`。正确的 API 输入 layout 为 NHWC，输出为 NCHW。此前以 NCHW 输入调用触发 Runtime 不支持的 normalize 路径，该试验的超时不计入有效输入的压测结果。

试运行用的 Runtime、模型、验证程序和进程级 heap 切换脚本在板端 `~/.local/share/z96a-rknn-2.3.2/`。当前设备节点权限为 `0600 root:root`，实机命令使用 `sudo`。

```sh
cd ~/.local/share/z96a-rknn-2.3.2
sudo ./run-uncached.sh ./conv-check conv.rknn 30
```

本机 `local/npu/trial/` 保存 DTB 差异、串口、对照和采样原始日志。Runtime、演示模型和参考输出来自同一官方 Git tag 的 Linux Runtime、`rknn_mobilenet_demo`、`rknn-toolkit2/examples/tflite/mobilenet_v1` 与 `rknn-toolkit-lite2/examples/resnet18`。
